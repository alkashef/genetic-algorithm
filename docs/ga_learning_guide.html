Core GA Lifecycle

This tab contains concepts that apply broadly to genetic algorithms. Domain-specific choices are moved to the TSP and Timetable tabs.

0Problem framing & representation

partly covered

Core idea: before a GA can run, one candidate solution must be encoded as a genome/chromosome.

List of techniques

  • Binary encoding
  • Integer/vector encoding
  • Real-valued encoding
  • Permutation encoding
  • Assignment/matrix encoding
  • Tree/program encoding

Focus section

We focused on the principle that the genome must match the problem structure. A bad representation makes crossover/mutation invalid or meaningless.

Takeaways

  • Representation is not a coding detail; it shapes the search.
  • Operators must respect the representation.
  • Validity is easier when the representation is designed well.

1Initialization

still need to cover

Core idea: initialization creates the first population. It controls starting diversity and starting quality.

List of techniques

  • Pure random initialization
  • Heuristic-seeded initialization
  • Mixed random + heuristic initialization
  • Diversity-aware initialization
  • Repair-after-initialization

Focus section

Next focus: mixed initialization. It starts with broad random coverage but injects a few good heuristic candidates so the GA does not start blindly.

Takeaways

  • Random-only gives diversity but may start weak.
  • Heuristic-only may reduce diversity.
  • Mixed initialization is usually safest.

2Fitness evaluation

covered basics

Core idea: the fitness function scores how good each genome is. It is the GA's definition of success.

List of techniques

  • Direct objective score
  • Penalty-based fitness
  • Feasibility-first scoring
  • Weighted multi-criteria fitness
  • Noisy/averaged fitness
  • Multi-objective fitness

Focus section

We focused on the simple version: compute a score for each genome, then use that score to guide selection.

Takeaways

  • Fitness is where the problem becomes measurable.
  • Bad fitness produces bad learning.
  • For real problems, constraints often dominate fitness design.

3Selection

covered

Core idea: selection chooses which genomes become parents. It does not create children and does not mutate.

List of techniques

  • Roulette wheel selection
  • Rank selection
  • Tournament selection
  • Stochastic universal sampling
  • Truncation selection
  • Selection with replacement

Focus section

Tournament selection: randomly choose k genomes; the best among them becomes a parent. Start with k = 3.

parent = best(randomly_choose(population, k=3))

Takeaways

  • k controls selection pressure.
  • k = 1 means random selection.
  • Large k can collapse diversity.
  • A strong genome may be selected multiple times.

4Crossover

covered concept

Core idea: crossover combines information from two parents to create children.

List of techniques

  • One-point crossover
  • Two-point crossover
  • Uniform crossover
  • Blend/arithmetic crossover
  • Validity-preserving crossover
  • Representation-specific crossover

Focus section

We focused on the rule that crossover must fit the genome representation. For structured problems, generic crossover can produce invalid children.

Takeaways

  • Crossover is recombination, not randomness alone.
  • Crossover rate controls how often selected parents recombine.
  • Practical starting rate: 0.80–0.95, often 0.90.

5Mutation

covered concept

Core idea: mutation adds controlled variation so the population does not become too narrow.

List of techniques

  • Bit-flip mutation
  • Random-reset mutation
  • Gaussian mutation
  • Swap-like mutation
  • Segment/change mutation
  • Adaptive mutation

Focus section

We focused on the distinction between mutation rate and mutation strength.

  • Rate = how often mutation happens.
  • Strength = how large the change is.

Takeaways

  • Too little mutation → stuck.
  • Too much mutation → near-random search.
  • If diversity is low and progress stalls, increase mutation temporarily.

6Replacement strategy & elitism

covered

Core idea: replacement decides who enters the next generation after children are created.

List of techniques

  • Generational replacement
  • Elitist generational replacement
  • Steady-state GA
  • Replace-worst strategy
  • Age-based replacement

Focus section

Elitist generational replacement: copy a few best old genomes unchanged, then fill the rest with new children.

new_population = elites + children

Takeaways

  • Elitism protects progress.
  • Too much elitism kills diversity.
  • Elites can also be selected as parents.
  • For population 100, start with 1–2 elites.

7Hyperparameters

covered basics

Core idea: hyperparameters are the knobs that control GA behavior.

List of knobs

  • Population size
  • Elite count
  • Tournament size k
  • Crossover rate
  • Mutation rate
  • Mutation strength
  • Max generations
  • Evaluation/time budget

Focus section

We focused on a practical starting profile:

population_size = 100 elite_count = 2 tournament_k = 3 crossover_rate = 0.90 mutation_rate = 0.10

Takeaways

  • No fixed ratio exists between answer-space size and population size.
  • Population size scales with problem size, diversity need, and compute budget.
  • Total search budget = population_size × generations.

8Termination criteria

still need to cover

Core idea: termination decides when the GA stops running.

List of techniques

  • Maximum generations
  • No improvement for N generations
  • Target fitness reached
  • Time budget reached
  • Evaluation budget reached
  • Diversity collapse stop/restart rule

Focus section

Next focus: combine max generations with stagnation stopping.

stop if generation == max_generations or no_improvement > patience

Takeaways

  • Stopping by generation alone is simple but blind.
  • Stagnation detection is more practical.
  • For real use, stop rules should match compute budget.

9Diagnostics

still need to cover

Core idea: diagnostics tell you whether the GA is healthy, stuck, too random, or converging too fast.

List of techniques

  • Best fitness curve
  • Average/median fitness curve
  • Worst fitness curve
  • Fitness spread
  • Diversity measure
  • Stagnation counter
  • Operator success rates

Focus section

Next focus: dashboard-style diagnostics. The dashboard tab lists the exact knobs, curves, and alerts to implement.

Takeaways

  • One best score is not enough.
  • Track both performance and diversity.
  • Diagnostics guide parameter tuning.

10Constraint handling

still need to cover deeply

Core idea: real GA problems often have invalid solutions. You need a rule for invalid genomes.

List of techniques

  • Valid operators only
  • Repair invalid genomes
  • Penalty functions
  • Reject invalid children
  • Feasibility-first selection
  • Decoder-based representation

Focus section

Next focus: compare repair vs penalty vs valid operators, because the best choice depends heavily on the problem.

Takeaways

  • Hard constraints should not be treated like minor preferences.
  • Repair can save useful genetic material.
  • Penalties need careful weighting.

11Hybrid GA / memetic algorithms

still need to cover

Core idea: combine GA's global exploration with a local search that improves individual solutions.

List of techniques

  • GA + local search
  • GA + hill climbing
  • GA + simulated annealing
  • GA + problem heuristic
  • Lamarckian update: replace genome with improved version
  • Baldwinian update: fitness improves without replacing genome

Focus section

Next focus: when to run local search: on every child, only elites, periodically, or only late in the run.

Takeaways

  • Plain GA is often not enough for strong performance.
  • Hybridization usually improves real implementations.
  • Local search increases compute cost, so apply selectively.

12Benchmarking, reproducibility & scaling

still need to cover

Core idea: real GA work must prove that the algorithm is better than simple baselines and that results are reproducible.

List of techniques

  • Random-search baseline
  • Greedy baseline
  • Exact/brute-force comparison for tiny cases
  • Known benchmark instances
  • Multiple random seeds
  • Parameter sweep experiments
  • Fitness caching
  • Parallel evaluation

Focus section

Next focus: multiple runs with fixed seeds and a comparison table: best, average, standard deviation, and runtime.

Takeaways

  • One GA run is not evidence.
  • Compare against simple baselines first.
  • Track seeds, parameters, runtime, and final score.

TSP Specifics — only what is special for route optimization

This tab excludes generic GA mechanics already covered in Core GA. It keeps only route/TSP-specific choices.

Representation

TSP-specific

Techniques

  • Permutation route
  • Closed tour representation
  • Canonicalized tour to reduce duplicates

Focus

One genome is an ordered route containing every city exactly once.

[A, B, C, D, E]

Takeaways

  • Same cities appear in every genome.
  • Quality comes from city adjacencies/edges.
  • Index position alone is not the key signal.

Search space

TSP-specific

Techniques

  • Directed tour count
  • Symmetric tour count
  • Fix start city to avoid rotations
  • Normalize direction when symmetric

Focus

For symmetric TSP, the number of unique tours is approximately:

(n - 1)! / 2

Takeaways

  • Search space grows factorially.
  • Population never covers a meaningful percentage.
  • Total evaluations matter more than coverage ratio.

TSP operators

InitializationRandom permutations; greedy/nearest-neighbor seeds; mixed random + heuristic seedsRandom routes as baseline; heuristic seeding still to coverKeep diversity; do not fill the whole population with one greedy pattern.
FitnessTotal tour distance; closed-loop distance; optional penalties for invalid routesShorter route = better fitnessFor minimization, lower distance is better; often convert to score if the GA expects maximization.
CrossoverOX; PMX; CX; edge recombination; edge assemblyOX / Order CrossoverOX preserves a slice + relative order and keeps routes valid. It does not strongly preserve edges.
MutationSwap; inversion; insert; scrambleInversion mutationInversion is natural for routes because it changes edges while keeping a valid permutation.

Recommended first serious TSP GA setup

representation = permutation_route fitness = total_closed_tour_distance selection = tournament(k=3) crossover = OX crossover_rate = 0.90 mutation = inversion mutation_rate = 0.10 replacement = elitist_generational elite_count = 2 population_size = 100 termination = max_generations + stagnation_patience
TSP-specific key lesson: route quality is mostly about edges/adjacencies, so diagnostics and advanced crossover should eventually become edge-aware.

Timetable Specifics — only what is special for scheduling

This tab excludes generic GA mechanics already covered in Core GA. It keeps only timetable-specific modeling, constraints, operators, and diagnostics.

Timetable representation

timetable-specific

Techniques

  • Event-to-slot assignment
  • Event-to-slot-room assignment
  • Matrix timetable representation
  • Decoder representation

Focus

One genome is one full timetable: each event/class is assigned to a time slot and usually a room.

event_i → (day, period, room)

Takeaways

  • The genome is an assignment, not a simple route.
  • Feasibility is harder than in TSP.
  • Representation should make impossible conflicts less likely.

Hard vs soft constraints

timetable-specific

Hard constraints

  • Teacher cannot teach two classes at once
  • Room cannot host two classes at once
  • Student group cannot attend two classes at once
  • Room capacity/equipment must fit
  • Teacher/room availability must be respected

Soft constraints

  • Minimize teacher gaps
  • Avoid very early/late sessions
  • Spread load across days
  • Prefer certain rooms
  • Improve fairness of schedules

Takeaways

  • Hard constraints define validity.
  • Soft constraints define quality.
  • Penalty weights are critical and easy to get wrong.

Timetable operators

Lifecycle stepTimetable-specific techniquesBest practical focusImportant lessons

CrossoverDay-block crossover; class-group block crossover; teacher-block crossover; repair-after-crossoverBlock crossover + repairNaive crossover can destroy feasibility. Preserve meaningful timetable blocks.

Recommended first timetable GA setup

representation = event_to_slot_room_assignment fitness = hard_violation_penalty + soft_preference_penalty selection = tournament(k=3) crossover = block_crossover + repair mutation = move_or_swap_conflicting_event mutation_strategy = conflict_directed_when_invalid replacement = elitist_generational elite_rule = keep_best_feasible_or_lowest_violation termination = time_budget + stagnation_patience
Timetable-specific key lesson: the central challenge is not just optimization. It is maintaining or recovering feasibility under many hard constraints.

Dashboard — knobs, algorithm choices, curves, and alerts

This tab defines what a real GA implementation should expose and track. Think of it as the control panel for experimentation, tuning, and debugging.

Global parameters

  • Random seed
  • Population size
  • Max generations
  • Max evaluations
  • Time budget
  • Objective direction: minimize/maximize
  • Number of repeated runs
  • Parallel evaluation on/off
  • Duplicate genome handling
  • Restart policy

Algorithm choices

  • Representation type
  • Initialization method
  • Selection method + parameters
  • Crossover operator + rate
  • Mutation operator + rate + strength
  • Replacement strategy
  • Elitism on/off + elite count
  • Constraint handling method
  • Repair operator on/off
  • Local search / hybridization on/off

Adaptive controls

  • Increase mutation if diversity is low
  • Decrease mutation if search is unstable
  • Reduce selection pressure if elites dominate
  • Increase selection pressure if progress is too slow
  • Trigger restart after long stagnation
  • Enable local search late in the run
  • Stop when target or patience is reached

Curves to plot per generation

Fitness curvesBest fitness, average fitness, median fitness, worst fitness, fitness spread.
Diversity curvesUnique genome count, representation-specific diversity, duplicate rate, elite dominance.
Convergence curvesStagnation counter, generations since best improvement, improvement per generation.
Operator curvesCrossover success rate, mutation success rate, repair success rate, local-search improvement.
Constraint curvesFeasible ratio, hard violation count, soft penalty score, violation type breakdown.
Performance curvesEvaluation time, generation runtime, cache hit rate, evaluations per second.

Dashboard cards/tables

Dashboard elementWhat it showsWhy it matters
Current best genomeBest solution, fitness, generation foundTracks the best result so far.
Run configurationSeed, population, rates, operators, constraintsMakes runs reproducible.
Top-k elitesBest few genomes and similarity between themDetects elite domination.
Population snapshotDiversity, duplicates, fitness spreadShows population health.
Experiment comparisonMultiple runs by parameter settingSupports tuning by evidence, not guessing.
Baseline comparisonGA vs random, greedy, brute force small casesProves the GA adds value.

Alerts to implement

  • Premature convergence Diversity below threshold while best fitness stagnates.
  • Too random Fitness jumps wildly and average does not improve.
  • Elite domination Top genomes occupy too much of the population.
  • No feasible solutions Feasible ratio stays near zero.
  • Duplicate population Duplicate genome rate is high.
  • Slow run Evaluation time dominates runtime.

Run summary metrics

  • Best final fitness
  • Mean final fitness across runs
  • Standard deviation across runs
  • Best generation found
  • Total evaluations
  • Total runtime
  • Feasible solution rate
  • Improvement over baseline
